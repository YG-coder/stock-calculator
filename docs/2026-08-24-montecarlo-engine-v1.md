## 2. 입력 변수와 단위

| 필드 | 단위 | 의미 | 비고 |
|---|---|---|---|
| `seed` | 정수 | 난수 시드 | 결과에 그대로 실려 나온다 |
| `paths` | 개 | 경로 수 | 1 ~ 50,000 |
| `months` | 개월 | 총 기간 | 1 ~ 720 |
| `initialBalance` | 원(명목) | 초기 자산 | 0 이상 |
| `cashFlow.monthlyAmount` | 원(명목) | 월 현금흐름 | **양수 = 적립, 음수 = 인출.** `type` 필드 없음 |
| `cashFlow.timing` | — | `"start"` / `"end"` | 필수. 숨은 기본값 없음 |
| `cashFlow.inflationIndexed` | — | 매년 물가만큼 증액 | 배수 `(1+π)^floor(m/12)` |
| `cashFlow.fromMonth` / `toMonth` | 개월 | 적용 구간 | **반열림 `[from, to)`** |
| `cashFlow.overrides` | 원 | 월별 일시금 | 해당 월 `monthlyAmount` 에 **더해진다**(치환 아님) |
| `returns.expectedReturn` | 실수 | 연 **CAGR**(기하평균, 명목, 총수익) | 산술평균이 아니다 |
| `returns.volatility` | 실수 | 연 변동성, **단순수익률 기준** | 0 ~ 0.45 |
| `returns.shock` | — | 충격 분포 | 기본 `{student-t, df 6}`. v1 은 df 6 고정 |
| `inflationRate` | 실수 | 연 물가상승률 | **엔진에 기본값 없음.** 호출부가 명시 |
| `reportBasis` | — | `"nominal"` / `"real"` | 화면 권장 기본은 `real` |
| `goal.targetAmount` | 원 | 목표 금액 | `reportBasis` 와 **같은 기준**으로 해석 |
| `goal.targetProbability` | 0~1 | 목표 확률 | 주어지면 역산 수행 |

**입력 범위를 벗어나면 조용히 클램프하지 않고 거부한다.** 기존 계산기 감사에서 지적된
"음수를 조용히 0으로 치환" 패턴을 반복하지 않기 위한 규칙이다. 오류는 필드별 사유
(`ValidationIssue[]`)로 돌아간다.

## 3. 월별 계산 순서

```
for m in 0 .. months-1:
    flow = c · shape[m] + overrides[m]
    if timing == "start":  balance += flow
    balance *= returnFactor[m]
    if timing == "end":    balance += flow
    if 잔액이 0 이하로 떨어졌다면 (양수였던 경로에 한해):
        balance = 0; 소진 시점 기록; 경로 종료
    if 연 단위 그리드 시점이면:  기록 (reportBasis 가 "real" 이면 이때 환산)
```

- **납입 시점을 숨기지 않는다.** 기존 복리 계산기는 기말(ordinary annuity) 기준이었는데
  화면에 표기가 없어 감사에서 지적됐다. 여기서는 `timing` 을 필수 입력으로 받는다.
- **진행 계산은 항상 명목으로 돈다.** 실질 환산은 기록 단계에서만 한다 — 이중 할인 방지.
  덕분에 명목/실질 토글이 재시뮬레이션 없이 즉시 전환된다.
- **소진 판정**: "잔액이 양수였다가 0 이하로 떨어진 사건"으로 정의한다. 아직 한 번도
  양수인 적이 없는 0(예: `fromMonth = 6` 처럼 납입이 나중에 시작하는 구간 설정, FIRE 의
  적립 전 구간)은 소진이 아니다. 단순히 `balance <= 0` 으로 판정하면 정상 시나리오가
  첫 달에 종료된다 — 구현 중 실제로 발견해 고친 지점이다.

## 4. 연 → 월 변환 (`returns.ts` 한 곳에서만)

### 4-1. 드리프트

```
μ_m = ln(1 + CAGR) / 12
```

충격의 중앙값이 0 이므로(정규·t 모두 대칭) **중앙값 경로가 정확히 입력 CAGR 로 복리된다.**
드리프트를 로그 공간에서 먼저 고정하므로 충격 분포를 바꿔도 중심 경향은 유지되고 꼬리만 달라진다.

산술평균 → 로그정규 변환식 `μ_log = ln(1+μ_a) − σ_log²/2` 는 **쓰지 않는다.** 산술평균 입력을
전제로 `E[gross] = 1+μ_a` 를 맞추는 보정인데, t 충격에서는 `exp(σz)` 의 기댓값 자체가 발산해
의미를 잃는다. 입력을 CAGR 로 정의하면 이 보정이 애초에 필요 없다.

### 4-2. 변동성 — 캘리브레이션 테이블 역보간

입력 변동성은 **단순수익률 기준**이다(사용자가 떠올리는 "주식 변동성 15%"의 의미).
로그정규 폐형식은 쓰지 않는다. 대신 절단된 t 충격 아래에서의 실제 연 분산을 역산한다.

```
M(a)   = E[exp(a·z)]                       z = t_6·sqrt(4/6), |z| ≤ 8 재추출
E[1+R] = (1+CAGR)·M(σ_m)^12
Var(R) = (1+CAGR)²·(M(2σ_m)^12 − M(σ_m)^24)

⇒  u ≡ σ_target/(1+CAGR) = sqrt( M(2σ_m)^12 − M(σ_m)^24 )
```

**CAGR 이 소거된다.** `u` 는 `σ_m` 만의 단조 함수이므로 1차원 역함수 테이블 하나로 끝난다.
`scripts/gen-sigma-table.mjs` 가 `σ_m ∈ [0, 0.15]` 201점 테이블을 만들고, 런타임은 단조
역보간만 한다. 브라우저에 감마 함수도, 적분도, 몬테카를로 캘리브레이션도 필요 없다.

**생성기 자기검증값** (설계 문서의 예측값과 대조)

| 항목 | 실측 | 설계 문서 |
|---|---|---|
| 절단 후 `z` 표준편차 | `0.996848` | 0.99685 ✅ |
| 구간 중점 선형보간 최대 상대오차 | `4.98e-06` | 4.9e-06 ✅ |
| `toMonthlyParams(0.07, 0.15).sigmaM` | `0.039978089` | 0.0399782 ✅ |
| CAGR 0 / 7 / 20 / 50% 에서 같은 `u` → 같은 `σ_m` | 12자리 일치 | 9자리 일치 ✅ |

**MC 캘리브레이션을 쓰지 않는 이유**: 시드마다 답이 달라져 재현성 원칙과 충돌하고,
정밀도를 올리려면 캘리브레이션이 시뮬레이션보다 비싸진다.

### 4-3. 발견한 문서 불일치 2건

1. 구현 계획 §5 테스트 3번의 `σ_log ≈ 0.1395` 는 **쓰지 않기로 한 로그정규 폐형식의 값**이다.
   캘리브레이션 값은 연환산 `0.13849` 로, 두 값의 비 `1.0073` 이 같은 문서가 적어 둔
   "로그정규식 사용 시 +0.76%" 오차와 정확히 일치한다. 테스트는 캘리브레이션 값 기준으로 썼고,
   두 값의 차이 자체를 별도 테스트로 남겨 관례 혼동을 코드로 고정했다.
2. 자산 가정 문서 §8 의 "커버 가능한 입력 σ 최대"(CAGR 0% → 47.7% 등)는 실측과 다르다.
   실제 테이블 상한은 `u_max = 0.64568` 이므로 CAGR 0% 에서 σ 64.6% 까지 덮는다.
   **다만 방향은 문서가 맞다** — `CAGR ∈ [−0.5, 0.5]`, `σ ∈ [0, 0.45]` 를 각각 허용하면
   CAGR 이 음수일 때 조합이 테이블을 벗어난다(예: CAGR −50%, σ 45% → `u = 0.9`).
   조용히 클램프하지 않고 **별도 입력 오류**로 거부한다.

## 5. 난수와 충격 분포

| 항목 | 구현 |
|---|---|
| 균등난수 | xoshiro128\*\* (32비트 4워드), 시드 확장 splitmix32 |
| 정규난수 | Marsaglia polar (Box–Muller 극좌표형), 두 번째 값 캐시 |
| chi2(6) | 지수분포 3개의 합 → `-2·ln(u₁u₂u₃)`, 로그 1회 |
| Student's t | `t_ν = Z·sqrt(ν/V)`, `V ~ chi2(ν)` |
| 단위분산 보정 | `z = t_ν·sqrt((ν−2)/ν)` — **빠뜨리면 df 6 에서 σ 가 1.2247배(+22.5%) 부푼다** |
| 절단 | `\|z\| > 8` 재추출. **재정규화하지 않는다** |
| 월 수익 배수 | `exp(μ_m + σ_m·z)` |

`Math.random()` 은 시드를 줄 수 없어 쓰지 않는다.

**절단 계약**: 재추출은 조건부 분포를 만들어 표본 σ 가 입력값보다 최대 0.32% 작아진다.
재정규화는 보정을 한 번 더 하는 코드를 늘려 실수 여지를 만들 뿐이므로 하지 않고,
"수치 절단으로 표본 σ 가 입력값보다 최대 0.4% 작을 수 있다"를 계약으로 명시한다.
검증 허용 오차 2% 와 자릿수가 달라 보정 누락(+22.5%)과 확실히 구분된다.

`meta.truncatedShocks` 는 성능 계측이 아니라 **정합성 경보**다. 실측 절단 비율은
`6.5e-05` 로 이론값 `6.51e-05` 와 일치한다(4.8M 표본 기준 312회).

### σ = 0 회귀 앵커가 충격 분포와 무관한 이유

`σ_m = 0` 이면 `exp(μ_m + 0·z) = exp(μ_m)` 로 충격이 소거된다. 따라서 Student's t 로 바꿔도
결정론 축소 테스트는 그대로 성립한다.

## 6. 상관관계 처리

**v1 은 단일 포트폴리오 수준 가정만 받는다.** 자산별 분해는 표시용이고 계산에 쓰지 않는다.

이유는 합성 규칙이다. 자산별 σ 를 단순 가중합하면 상관계수 1 을 가정하는 것과 같아
60/40(주식 σ15%, 채권 σ5%)에서 ρ=0 이면 실제 9.22% 를 11.00% 로 **19.3% 과대추정**한다.
캘리브레이션 오차를 2% 이내로 맞춰 놓고 입력에서 15% 를 틀리면 앞의 정밀도가 의미를 잃는다.

`correlation.ts` 에 상관행렬 검증(정사각·대각 1·대칭·범위·양의 준정부호)과 Cholesky 분해,
비중 검증(합 1·음수 거부)을 **순수 유틸로 미리 두되 엔진 경로에서는 호출하지 않는다.**
6단계 무매도 리밸런싱에서 다자산 `ReturnSpec` 이 들어올 때 이 규칙을 그대로 쓴다.
`ReturnSpec` 이 유니온 타입이므로 `{ kind: "multi-asset", weights, correlations }` 를
추가하고 `ReturnGenerator` 구현을 하나 더 만드는 것으로 끝난다 — **엔진은 수정되지 않는다.**

## 7. 세금·수수료·인플레이션

| 항목 | v1 처리 |
|---|---|
| 세금 | **계산하지 않는다.** 엔진에 세율이 없다 |
| 거래비용 | 계산하지 않는다 |
| 배당 | "미반영"이 아니라 **총수익(total return)에 내포**되어 있다 |
| 인플레이션 | 진행은 명목, 기록 시 실질 환산. 현금흐름 물가 연동은 선택 입력 |
| 환율·리밸런싱 | v1 범위 밖 |

세금을 넣지 않는 이유는 편의가 아니다. 과세는 계좌 종류·실현 시점·손익통산에 따라 모형이
갈리고, **경로가 상태 의존이 되어 선형 정확 역산이 깨진다.** 4단계 이후 별도 설계로 다룬다.

결과의 `meta.warnings` 에 다음이 항상 실려 나가며 화면은 이를 반드시 노출한다.

> 수익률은 배당을 재투자한 총수익 기준입니다. 세금과 거래비용은 반영하지 않았습니다.
> 성공확률은 입력한 가정에 대한 조건부 확률입니다. 실제 결과를 보장하지 않습니다.

물가상승률 기본값(연 2.0%, 한국은행 물가안정목표, 기준일 2026-08-22)은 **데이터 계층
(`presets.ts`)에만** 있다. 엔진은 `inflationRate` 를 필수 입력으로 받아 숨은 기본값을 만들지 않는다.

## 8. 성공확률과 목표 역산

### 정의

성공확률은 **가정에 대한 조건부 확률**이다.

```
successProbability = #{ 경로 j : W_T(j) ≥ W* } / N
```

`W_T` 와 `W*` 는 모두 `reportBasis` 기준으로 비교한다. 화면 문구 규칙은 다음과 같다.

- 쓴다: "이 가정에서 80% 시나리오가 목표를 달성"
- 쓰지 않는다: "80% 확률로 달성" / "80% 보장"

### 선형 정확 역산 (이분 탐색 아님)

한 경로의 월 수익 배수를 고정하면 종말자산은 납입 수준 `c` 에 대해 아핀이다.

```
W_T(c) = A_j + c·B_j
  A_j : 초기자산 + 일시금(overrides) 이 만기까지 불어난 값 — c 와 무관
  B_j : 월 1원 납입이 만기까지 누적된 값 — 현금흐름 형상에만 의존
```

`A`, `B` 는 시뮬레이션 **한 번의 패스에서 함께 누적**된다. 이후 목표 금액·목표 확률·납입액을
아무리 바꿔도 재시뮬레이션이 필요 없다 — 목표달성확률 화면의 슬라이더 3개가 실시간으로
움직일 수 있는 이유다.

```
c_j = (W* − A_j) / B_j          (B_j > 0)
c*  = c_j 의 p 분위수            ← p 분위수이지 1−p 가 아니다
```

인덱스 규칙은 `ceil(p·N) − 1` (0-based)로 고정한다. `floor` 를 쓰면 한 칸 보수적으로 치우친다.
`B_j ≤ 0` 인 경로(일시금만 있는 시나리오)는 납입액과 무관하게 성패가 고정되므로 분위수에서
제외하고 성공 카운트에 상수로 더한다. 이를 반영한 일반식은 `k = ceil(p·N) − fixedSuccesses` 다.

**선형성이 깨지는 조건** — 잔액이 0 에 클램프되거나 경로 의존 규칙이 들어가면 성립하지 않는다.
엔진이 클램프를 감지하면 `affine` 을 **아예 만들지 않고** 경고를 남긴다. 호출부는 `affine` 의
존재 여부만 보고 선형 역산과 이분 탐색을 가른다 — 판단 로직이 UI 에 흩어지지 않는다.

**부동소수 경계 주의**: `c*` 는 경계 경로의 종말자산이 목표와 정확히 같아지는 값이므로,
`A + c*·B` 가 마지막 비트에서 목표를 근소하게 밑돌아 재시뮬 성공확률이 1경로(1/N)만큼
낮게 나올 수 있다. 경험적 CDF 기준(`successProbabilityAt`)은 정확히 목표 이상이다.

## 9. Web Worker

```
컴포넌트 → useMonteCarlo (디바운스) → worker-client → Worker → engine
```

**동기 루프로는 취소가 동작하지 않는다.** Worker 안에서 계산이 CPU 를 붙잡고 도는 동안
Worker 의 이벤트 루프가 멈춰 있어, 메인 스레드가 보낸 `cancel` 메시지는 큐에 쌓이기만 하고
핸들러가 실행되지 않는다. 루프 안에서 플래그를 아무리 자주 읽어도 값이 갱신되지 않는다.

채택한 구조는 **배치 실행 후 이벤트 루프에 제어 반환**이다.

- `yieldToEventLoop()` 는 `MessageChannel` 기반. `setTimeout(0)` 은 중첩 시 4ms 로 클램프된다.
- 배치 크기는 **시간 기준 적응** — 첫 배치 200경로로 재고, 이후 한 배치가 약 50ms 가 되도록 조정.
  경로당 비용이 기간에 따라 10배 이상 차이나므로 고정 개수는 나쁘다.
- 취소 지연은 배치 하나(≈50ms) 이내.
- 진행률은 250ms 미만 간격으로 보내지 않는다.
- 요청 id 로 오래된 결과를 버린다. 새 `run` 이 오면 이전 실행을 자동 취소한다.
- 결과의 typed array 는 **transfer** 로 넘겨 복사를 피한다(버퍼 중복은 제거).
- Worker 미지원·생성 실패 시 메인 스레드 동기 실행으로 폴백하되 경로 수를 2,000 으로 낮추고
  **그 사실을 경고로 알린다.**
- `SharedArrayBuffer` + `Atomics` 는 쓰지 않는다 — 교차 출처 격리(COOP/COEP) 헤더가 필요한데
  그러면 애드센스 스크립트 로딩이 깨진다.
- 훅은 언마운트 시 Worker 를 정리하고, 계산 중에도 이전 결과를 유지한다(깜빡임 방지).

전부 클라이언트 사이드이므로 Cloudflare/OpenNext 엣지 런타임과 무관하다.

### 병목과 최적화 기록

첫 구현은 같은 조건에서 **1,461ms** 로 예산을 46% 초과했다. 프로파일 결과 원인은

| 조치 | 효과 |
|---|---|
| xoshiro128\*\* 상태를 uint32 정규화 → **int32 유지**(출력만 부호 제거) | 난수 생성 24.5M/s → 54.3M/s |

비트 패턴은 동일하므로 `>>> 0` 은 순전히 JS 숫자 표현 비용이었다.
`Math.exp`/`log`/`sqrt` 는 200M/s 수준으로 병목이 아니었다.

> 참고: 두 번째 조치로 난수 소비 **순서**가 바뀌었다(정규 → chi2 에서 chi2 → 정규).
> 통계적으로 동등하지만 같은 시드의 수열이 달라지므로 스냅샷을 재생성했다.

### 12-1. 기존 복리 계산기 회귀 — **원 단위 일치**

`volatility = 0`, `inflationRate = 0`, `inflationIndexed = false`, `reportBasis = "nominal"`,
`timing = "end"` 조건에서 폐형식과 비교한다.

**비교 대상은 컴포넌트가 아니라 테스트 안에 직접 옮겨 적은 폐형식이다.** 두 계산기의
복리 관례가 다르기 때문이다.

| | 월 성장 배수 | 연 실효 |
|---|---|---|
| 기존 복리 계산기 | `1 + r/12` (명목 연이율) | `(1+r/12)¹² − 1` |
| MonteCarloEngine | `(1+CAGR)^(1/12)` | `CAGR` 정확히 |

`CAGR = (1+r/12)¹² − 1` 로 변환해야 맞는다. 이 변환 자체를 보조 테스트로 남겼다.

## 14. 알려진 한계

- **모형은 국면 전환을 담지 않는다.** iid 월간 충격이라 변동성 군집·평균회귀·자기상관이 없다.
  실제 시장의 연속 하락은 이 모형보다 길고 깊을 수 있다. 부트스트랩(8단계)이 이 한계를 겨눈다.
- **꼬리에서 평균이 불안정하다.** 로그수익률에 t 충격을 쓰면 `exp(σ·z)` 의 기댓값이 이론적으로
  발산한다. `Distribution.mean` 은 참고용으로만 두고 화면에서 강조하지 않는다.
- **단일 자산 가정.** 분산효과가 입력 숫자 안에 이미 들어 있다고 전제한다.
- **세금·거래비용·환율 미반영.**
- **`df = 6` 전역 고정.** 자산군마다 꼬리 두께가 다르지만 프리셋별 df 는 실제 데이터 추정과
  출처 관리가 따라와야 해서 복잡도 대비 이득이 작다고 판단했다. 바꾸려면 캘리브레이션
  테이블을 다시 생성해야 하며, 검증에서 이를 명시적으로 거부한다.
- **`volatility` 상한은 `σ/(1+CAGR) ≤ 0.6457`.** CAGR 이 음수면 실질 상한이 낮아진다.
- **성능 목표는 데스크톱 기준.** 모바일은 경로 수를 낮춰야 한다(2단계 UI 과제).
