### 변환이 일어나는 곳은 딱 하나 — 그리고 그 변환은 수치 캘리브레이션이다

연 단위 입력 → 월 로그 파라미터 변환은 **`returns.ts`에서만** 한다. 엔진과 테스트는 이미 변환된 `μ_m`, `σ_m`만 받는다.

**로그정규 변환식은 쓰지 않는다.** 초안에 있던

```ts
// ❌ 쓰지 않음
const sigmaLog = Math.sqrt(Math.log(1 + sigmaSimple**2 / (1+cagr)**2));
```

는 두 가지 이유로 이 모델과 맞지 않는다.

1. 이 식은 **산술평균 드리프트**(`E[R] = μ_a`)를 전제로 유도된 관계다. 우리는 드리프트를
   CAGR(중앙값) 기준으로 바꿨으므로 전제가 깨졌다. 충격이 정규분포여도 어긋난다.
2. 충격이 Student's t 면 로그정규 모멘트 관계 자체가 성립하지 않는다.

**실측 오차** (df 6, `|z| ≤ 8` 절단, 목표 대비 실현 단순 σ)

| CAGR | 목표 σ | 로그정규식 사용 시 실현 σ | 오차 |
|---|---|---|---|
| 7% | 15% | 0.1511 | **+0.76%** |
| 8% | 20% | 0.2031 | **+1.55%** |
| 7% | 25% | 0.2566 | **+2.65%** |
| 5% | 10% | 0.1002 | +0.18% |
| (참고) 정규 충격 | 15% | 0.1515 | +0.98% |

변동성이 클수록 커진다. 검증 기준 2%를 25% 구간에서 넘기므로 그냥 둘 수 없다.

### 캘리브레이션 방법 — MC 아닌 결정론적 역산

`z_i`가 iid이므로 연 단위 적률이 **1차원 적분의 12제곱**으로 닫힌다.

```
M(a) = E[ exp(a·z) ]        z = t_ν · sqrt((ν−2)/ν), |z| ≤ 8 로 절단
                            → 구간 [−8/k, 8/k] 위의 1차원 수치적분

E[1+R] = (1+CAGR) · M(σ_m)^12
Var(R) = (1+CAGR)² · ( M(2σ_m)^12 − M(σ_m)^24 )
```

**핵심 성질 — CAGR이 소거된다.** `Var(R)/(1+CAGR)²`는 `σ_m`만의 함수다.

```
g(σ_m) = M(2σ_m)^12 − M(σ_m)^24

목표:  sqrt( g(σ_m) ) = σ_target / (1 + CAGR)  ≡ u
```

즉 **CAGR과 무관한 1차원 단조 역함수** 하나만 있으면 된다. 수치 검증 결과 `u`가 같으면
CAGR 0%·7%·20%·50% 전부 `σ_m = 0.0399782`로 일치했다(9자리).

**구현**

- 빌드 타임 스크립트로 `σ_m ∈ [0, 0.15]` 200점에 대해 `sqrt(g(σ_m))` 테이블을 생성해 상수로 박는다.
  선형 보간 최대 상대오차 **4.9e-06** — 충분하다.
- 런타임은 테이블에서 단조 역보간만 한다. 브라우저에 감마 함수도, 적분도, MC도 필요 없다.
- MC 캘리브레이션을 쓰지 않는 이유: **시드마다 답이 달라진다.** 같은 입력에 같은 결과라는
  재현성 원칙과 충돌하고, 정밀도를 올리려면 캘리브레이션 자체가 시뮬레이션보다 비싸진다.

```ts
// returns.ts — 유일한 변환 지점
export function toMonthlyParams(cagr: number, sigmaSimple: number) {
  const u = sigmaSimple / (1 + cagr);
  return {
    muM: Math.log(1 + cagr) / 12,
    sigmaM: invertSigmaTable(u),   // 단조 역보간, df=6·절단8 고정 테이블
  };
}
```

`df`나 절단값을 바꾸면 테이블을 다시 생성해야 한다. **v1은 `df = 6` 전역 고정**이므로 테이블도 하나다.

## 3. 타입 최종본

계약 문서의 타입을 그대로 쓰되, 구현에 필요한 두 가지를 추가한다.

```ts
// 진행 상황 콜백 — 엔진이 Worker 를 모른 채 진행률을 알린다
export type ProgressFn = (completed: number, total: number) => void;

// 엔진 진입점
export function runSimulation(
  input: SimulationInput,
  opts?: { onProgress?: ProgressFn; shouldCancel?: () => boolean }
): SimulationResult;
```

`SimulationResult.affine`은 **클램프가 한 번도 발생하지 않은 실행에서만** 채운다. 인출 시나리오에서 잔액이 0에 닿으면 선형성이 깨지므로, 엔진이 클램프를 감지하면 `affine`을 `undefined`로 두고 호출부가 자동으로 이분 탐색으로 폴백한다. **판단을 UI에 맡기지 않는다.**

## 4. Worker 구조

```
컴포넌트 ──입력 변경──▶ useMonteCarlo (디바운스 300ms)
                              │
                              ├─ 이전 실행 있으면 cancel 메시지
                              └─ run 메시지 ──▶ Worker
                                                  │
                                                  ├─ engine.runSimulation()
                                                  ├─ progress (250ms 이상 간격)
                                                  └─ result (Float64Array transfer)
```

- Worker 생성은 `useEffect` 안에서만. `new Worker(new URL("../workers/montecarlo.worker.ts", import.meta.url))`.
- 인스턴스는 훅 수명 동안 **재사용**한다. 실행마다 새로 만들면 초기화 비용이 계산 시간을 넘긴다.
- 결과의 `Float64Array`는 transfer 목록에 실어 복사를 피한다.

### 취소가 실제로 동작하려면 — 배치 + yield

**동기 루프로는 취소가 불가능하다.** Worker 안에서 `runSimulation()`이 CPU를 붙잡고 도는 동안
Worker의 이벤트 루프는 멈춰 있다. 메인 스레드가 `postMessage({type:"cancel"})`을 보내도
**메시지가 큐에 쌓이기만 하고 핸들러가 실행되지 않는다.** 따라서 루프 안에서 `shouldCancel()`을
아무리 자주 호출해도 플래그 값이 갱신되지 않는다. 초안 설계는 이 지점에서 작동하지 않는다.

`SharedArrayBuffer` + `Atomics`로 플래그를 공유하는 방법은 **쓰지 않는다.** 교차 출처 격리
(COOP/COEP) 헤더가 필요한데, 그러면 애드센스 스크립트 로딩이 깨진다.

**채택: 배치 실행 후 이벤트 루프에 제어 반환.**

```
runner = createRunner(input)          // 상태를 가진 러너, 타이머·메시지를 모름
while (!runner.done) {
    runner.runBatch(batchSize)        // 동기 CPU 구간
    await yieldToEventLoop()          // ← 여기서 큐에 쌓인 cancel/run 이 처리된다
    if (cancelled) break
    postProgress()                    // 250ms 이상 간격일 때만
}
```

- `yieldToEventLoop()`는 `MessageChannel` 기반. `setTimeout(0)`은 중첩 시 4ms로 클램프되어
  배치가 많아지면 무시 못 할 오버헤드가 된다.
- **배치 크기는 시간 기준으로 적응**시킨다. 첫 배치를 200경로로 재보고, 이후 한 배치가
  약 50ms가 되도록 조정한다. 경로당 비용이 기간에 따라 10배 이상 차이나므로 고정 개수는 나쁘다.
- 취소 지연은 배치 하나(≈50ms) 이내. 슬라이더 조작 체감에 충분하다.
- 엔진의 순수성은 유지된다 — 러너는 **상태만 갖고 타이머·메시지를 모른다.** yield 책임은
  전적으로 Worker 쪽에 있다.

```ts
// engine.ts — 러너 인터페이스
export interface SimulationRunner {
  readonly done: boolean;
  readonly completed: number;
  readonly total: number;
  runBatch(paths: number): void;   // 동기. 완료 경로 수만큼 진행
  finish(): SimulationResult;      // done 이후 호출
}
export function createRunner(input: SimulationInput): SimulationRunner;
```

한 번에 끝내는 `runSimulation()`도 남긴다 — 테스트와 메인 스레드 폴백은 이쪽을 쓴다.
내부적으로 `createRunner` + 전량 `runBatch`이므로 코드 경로가 갈리지 않는다.
- **Cloudflare/OpenNext 영향 없음** — 전부 클라이언트 사이드다. 엣지 런타임과 무관.
- Worker 미지원·초기화 실패 시 메인 스레드 동기 실행으로 폴백하되, 경로 수를 2,000으로 낮춘다.

### 1번 회귀 앵커의 조건 고정

조건을 적어두지 않으면 나중에 "σ=0인데 왜 기존 계산기와 다르지?"라는 **거짓 실패**가 난다.
DCA 기본값이 `적립액 물가 연동 = 켬`이라 특히 그렇다. 테스트는 다음을 강제한다.

```
volatility        = 0
inflationRate     = 0
inflationIndexed  = false
reportBasis       = "nominal"
cashFlow.timing   = "end"
shock             = 무관 (σ=0 이면 소거됨)
```

**비교 대상은 기존 복리 계산기 컴포넌트가 아니라 테스트 안에 직접 쓴 폐형식이다.**
두 계산기의 복리 관례가 다르기 때문이다.

| | 월 성장 배수 | 연 실효 |
|---|---|---|
| 기존 복리 계산기 | `1 + r/12` (명목 연이율) | `(1+r/12)¹² − 1` |
| MonteCarloEngine | `(1+CAGR)^(1/12)` | `CAGR` 정확히 |

`r = 10%`면 기존 계산기의 연 실효는 10.47%다. **같은 숫자를 넣으면 당연히 다르게 나온다.**
두 결과를 맞추려면 `r = 12·((1+CAGR)^(1/12) − 1)`로 변환해야 한다.
이 변환 자체를 보조 테스트로 두어 두 계산기의 관례 차이를 문서 대신 코드로 남긴다.

6번을 두 값으로 하는 이유는 명확하다. **분위수 방향이 뒤집혀도 결과는 그럴듯한 숫자로 나온다.** `p`와 `1−p`가 대칭이 아닌 값을 골라야 자리 바꿈이 드러난다.

11번은 CI에서 실패시키지 않는다. 머신 편차가 커서 플레이키해진다 — 측정값을 출력만 하고 추세를 사람이 본다.

## 6. DCA 계산기 (2단계)

### 입력

| 필드 | 기본값 | 비고 |
|---|---|---|
| 초기 투자금 | 0 | |
| 월 적립액 | 500,000 | |
| 투자 기간 | 20년 | 슬라이더 1~40 |
| 자산 프리셋 | 선택 | 고르면 CAGR·σ 자동 입력, 이후 수정 가능 |
| 기대수익률 (CAGR) | 프리셋 값 | **"연복리 기준" 라벨 필수** |
| 변동성 | 프리셋 값 | **"단순수익률 기준" 라벨 필수** |
| 물가상승률 | 2.5% | 출처·기준일 필요 |
| 적립액 물가 연동 | 켬 | |
| 표시 기준 | 실질 | 명목/실질 토글 |

`시행 횟수`와 `시드`는 기본적으로 숨기고 "고급" 영역에 둔다. 시드는 결과에 항상 표시해 재현 가능하게 한다.

### 출력

1. **중앙값 최종 자산** — 가장 크게. 평균 아님
2. 팬 차트 — p5·p25·p50·p75·p95 밴드 + 대표 경로 몇 개
3. 최종 자산 분포 — p5 / p25 / **p50** / p75 / p95 표
4. 총 납입액 대비 배수
5. 가정 요약 블록 — CAGR·σ·df·물가·시드·기준일

### 흐름

```
입력 변경 → 300ms 디바운스 → Worker run → 진행률 바 → 결과 교체
```

계산 중에도 **이전 결과를 흐리게 유지**한다. 빈 화면으로 돌아가면 슬라이더를 움직일 때 깜빡인다.

### 표시 원칙

- 평균 대신 중앙값. `Distribution.mean`은 표에도 넣지 않는다 (t 꼬리에서 불안정)
- "수수료·세금 미반영" 고지를 결과 카드 안에
- 팬 차트 상단 밴드가 기대값처럼 보이지 않도록 p50 선만 진하게

## 7. 목표 달성 확률 계산기 (3단계)

### 이 계산기의 핵심 — 재시뮬레이션을 하지 않는다

`A_j`, `B_j`는 **시드·경로수·기간·수익률 가정·현금흐름 형상**에만 의존한다. 목표 금액 `W*`, 목표 확률 `p`, 납입 수준 `c`는 전혀 관여하지 않는다. 따라서 캐시 무효화 규칙이 이렇게 갈린다.

| 사용자 조작 | 재시뮬레이션 |
|---|---|
| 목표 금액 변경 | **불필요** |
| 목표 확률 슬라이더 | **불필요** |
| 월 납입액 슬라이더 | **불필요** (스칼라 `c`) |
| 기간·수익률·물가·물가연동 토글 변경 | 필요 |
| 시드·경로수 변경 | 필요 |

즉 **첫 실행 한 번이면 슬라이더 3개가 전부 실시간**이다. 이게 선형 역산을 택한 실질적 이유다.

### 양방향 조회

한 번 정렬해둔 `c_j` 배열 위에서 두 방향이 모두 즉시 답한다.

```
확률 → 납입액     c* = c_sorted[ ceil(p · N) − 1 ]              O(1)
납입액 → 확률     P(c) = (c_sorted 에서 c 이하 개수) / N        O(log N)  이진 탐색
```

**분위수 인덱스 규칙을 고정한다.** 오름차순 정렬 `c_(1) ≤ … ≤ c_(N)`에서 `k = ceil(p·N)`번째
값을 고르면 `#{j : c_j ≤ c*} ≥ k ≥ p·N` 이므로 **목표 확률을 만족하는 최소 납입액**이 된다.
0-based 인덱스로는 `ceil(p·N) − 1`. `N = 10,000`, `p = 0.9`면 인덱스 **8999**(9000번째 값)다.
`floor(p·N)`은 9001번째를 골라 한 칸 보수적으로 치우친다.

경계 처리: `p ≤ 0 → 0`, `p ≥ 1 → N−1`.

**`B_j = 0`인 경로 분리.** 납입이 전혀 없는 시나리오(일시금만)에서는 `B_j = 0`이라 `c_j`가
정의되지 않는다. 이 경로들은 납입액과 무관하게 `A_j ≥ W*` 여부로 성패가 고정되므로,
분위수 계산에서 제외하고 성공/실패 카운트에 상수로 더한다. `B_j > 0`인 경로가 하나도 없으면
역산 불가로 처리하고 UI에 사유를 표시한다.

정렬은 10,000개 기준 약 1ms. 슬라이더 `onInput`마다 다시 계산해도 프레임을 넘기지 않는다.

### 입력 추가분

- 목표 금액 (`W*`)
- 목표 확률 슬라이더 (50~95%, 기본 80%)
- 월 납입액 슬라이더 — 확률과 **연동**된다. 한쪽을 움직이면 다른 쪽이 따라온다

### 출력

- **"이 가정에서 목표 확률 80%를 맞추려면 월 XXX원"** — 주 결과
- 반대 방향: "월 XXX원이면 달성 확률 YY%"
- 확률–납입액 곡선 (`c_sorted`를 그대로 그리면 된다. 별도 계산 없음)
- 팬 차트에 목표 금액 수평선 오버레이

### 표시 원칙

확률은 **가정에 대한 조건부 확률**이다.

- 쓴다: "이 가정에서 80% 시나리오가 목표를 달성"
- 쓰지 않는다: "80% 확률로 달성" / "80% 보장"

`method: "linear-exact" | "bisection"` 값을 결과 하단에 조용히 노출한다. 나중에 FIRE와 결과가 다른 방식으로 나왔을 때 설명이 된다.

## 9. 남은 결정과 리스크

**착수 전 결정** (계약 문서 10절에서 이월)

1. 프리셋 수치의 출처 — 국내 장기 통계가 마땅치 않다. 해외 지수 기반으로 갈지, 범위로 제시할지
2. 물가상승률 기본값 2.5%의 근거·기준일
3. 결과 공유 방식 — **URL 직렬화는 권하지 않는다.** 개인 재무 정보가 URL에 남는다. 로컬 저장 우선

**확정된 것** (2026-08-22)

- **`df = 6` 전역 고정.** 자산별 df는 실제 데이터로 추정하고 출처까지 관리해야 해서
  복잡도 대비 이득이 작다. 캘리브레이션 테이블이 하나로 유지되는 이점도 크다.
- **v1(DCA·목표달성확률)은 세금을 계산하지 않는다.** "세금·수수료 미반영"을 결과 카드에 명시한다.
  과세를 넣으면 계좌 종류·실현 시점·손익통산에 따라 모델이 갈리고, **경로가 상태 의존이 되어
  선형 정확 역산이 깨진다.** 4단계 이후에 별도 설계로 다룬다.
