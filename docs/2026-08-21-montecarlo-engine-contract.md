# MonteCarloEngine 인터페이스 · 입출력 계약 (설계안)

- **작성일**: 2026-08-21
- **상태**: 설계 문서. **코드 변경 없음.** 애드센스 결과 확인 후 착수 여부 결정.
- **위치**: 플랫폼 확장 트랙(B) 1단계. 이후 DCA → 목표달성확률 → FIRE → SoRR → 리밸런싱 → 포트폴리오 → `/lab` 백테스트가 **전부 이 엔진을 참조**한다.

## 확정된 설계 결정

| 항목 | 결정 | 근거 |
|---|---|---|
| 수익률 생성 | **ReturnGenerator 인터페이스로 추상화.** 1단계는 파라메트릭만 구현하되 **충격 분포 기본값은 Student's t (df 6, 분산 보정)**, 정규/로그정규는 선택 옵션. 부트스트랩은 나중에 교체 | 엔진 본체를 데이터셋에 묶지 않기 위해. 월간 수익률의 꼬리는 정규보다 두껍다 — 정규 가정은 하방 시나리오를 낙관적으로 만든다 |
| 실행 환경 | **브라우저 Web Worker** | 서버 비용 0, 입력 데이터가 밖으로 나가지 않음(YMYL 민감 정보), UI 블로킹 회피 |
| 입력 방식 | **프리셋 + 직접 수정** | 진입장벽을 낮추되 사용자가 가정을 바꿀 수 있게. 단 프리셋 숫자는 근거와 기준일을 반드시 표기 |

## 1. 설계 원칙

1. **엔진은 순수 함수다.** DOM·React·fetch를 모르며, 입력 객체 하나를 받아 결과 객체 하나를 돌려준다. 테스트가 UI 없이 가능해야 한다.
2. **결정론적이다.** 시드를 입력에 포함한다. 같은 입력 + 같은 시드 = 항상 같은 결과. 이래야 스냅샷 테스트가 가능하고, URL로 시나리오를 공유할 수 있다.
3. **가정은 결과에 동봉된다.** 결과 객체가 사용된 가정을 그대로 되돌려준다. 화면에 "무엇을 전제로 한 숫자인지"를 항상 붙일 수 있어야 한다.
4. **시간 단위는 월로 고정한다.** DCA는 월 적립, SoRR은 월 인출이 기본이므로 월 단위가 최소공배수다. 연 단위 표시는 12스텝 집계로 만든다.
5. **모호한 규칙은 파라미터로 드러낸다.** 기존 복리 계산기에서 "연 수익률이 사실은 월복리", "납입이 기말 기준"이 화면에 없어 감사에서 지적됐다. 새 엔진은 이런 선택을 숨기지 않는다.
6. **세금·수수료는 훅으로 분리한다.** 엔진 내부에 세율을 박지 않는다. 필요하면 `lib/taxRates.ts`(품질 백로그 A2)를 주입한다.

export interface SimulationInput {
  /** 재현성을 위한 시드. 미지정 시 호출부에서 생성해 결과에 기록한다. */
  seed: number;

  /** 시뮬레이션 경로 수. 기본 10_000. 상한 50_000. */
  paths: number;

  /** 총 기간(개월). 40년 = 480. */
  months: number;

  /** 초기 자산 (원). */
  initialBalance: number;

  /** 월별 현금흐름. 양수 = 납입, 음수 = 인출. */
  cashFlow: CashFlowSpec;

  /** 수익률 생성기 설정. */
  returns: ReturnSpec;

  /** 물가 상승률(연, 실수). 실질 가치 환산과 현금흐름 인덱싱에 사용. */
  inflationRate: number;

  /** 결과를 명목/실질 중 무엇으로 보고할지. 기본 "real". */
  reportBasis: "nominal" | "real";

  /** 성공 판정 기준. 지정하지 않으면 successProbability 는 null. */
  goal?: GoalSpec;
}

export interface CashFlowSpec {
  /** 매월 금액. 음수면 인출. */
  monthlyAmount: number;

  /**
   * 적용 시점. 기존 복리 계산기가 기말(ordinary annuity) 기준이었으나
   * 화면에 표기가 없었다. 여기서는 명시적으로 받는다.
   */
  timing: "start" | "end";

  /** 물가에 연동해 매년 증액할지. 인출 시나리오에서 특히 중요. */
  inflationIndexed: boolean;

  /** 특정 구간에만 적용(예: 20년 적립 후 30년 인출). 미지정 시 전체 기간. */
  fromMonth?: number;
  toMonth?: number;

  /** 위 규칙으로 표현 못 하는 불규칙 현금흐름(일시금 등). monthIndex → 금액. */
  overrides?: Record<number, number>;
}

export type ReturnSpec =
  | {
      kind: "parametric";
      /** 연 CAGR(기하평균, 연복리). 산술평균이 아니다. 예: 0.07 */
      expectedReturn: number;
      /** 연 변동성(표준편차). 기준은 3-1절 결정 사항 참조. 예: 0.15 */
      volatility: number;
      /** 충격 분포. 미지정 시 { type: "student-t", df: 6 }. */
      shock?: ShockSpec;
    }
  | {
      kind: "bootstrap";
      /** 월별 수익률 시계열(실수 배열). 프리셋 데이터셋 id 로 참조. */
      datasetId: string;
      /** 블록 길이(개월). 1이면 iid, 12면 연 단위 블록. 자기상관 보존용. */
      blockMonths: number;
    };

/**
 * 로그수익률에 곱해지는 단위분산 충격.
 * 기본은 Student's t — 월간 수익률의 꼬리를 정규분포보다 잘 재현한다.
 */
export type ShockSpec =
  | { type: "student-t"; df: number }   // 권장 5~7, 기본 6. df > 2 필수
  | { type: "normal" };

export interface GoalSpec {
  /** "잔액이 0 아래로 내려가지 않음" 또는 "목표 금액 도달". */
  kind: "never-depleted" | "terminal-target";
  /** terminal-target 일 때의 목표 금액(원). */
  targetAmount?: number;
}

// ---------- 수익률 생성기 ----------

export interface ReturnGenerator {
  /** 한 경로에 대한 월별 수익률 배열을 채운다. 할당 없이 out 을 재사용한다. */
  fillPath(out: Float64Array, rng: Rng): void;
  /** 결과에 기록할 가정 요약. */
  describe(): ReturnAssumption;
}

export interface ReturnAssumption {
  kind: "parametric" | "bootstrap";
  label: string;              // "연 7.0% / 변동성 15.0% · 로그정규"
  source?: string;            // 부트스트랩일 때 데이터 출처
  asOf?: string;              // 프리셋 기준일 (YYYY-MM-DD)
}

// ---------- 출력 ----------

export interface SimulationResult {
  /** 입력 에코 + 실제 사용된 시드. */
  input: SimulationInput;
  assumptions: ReturnAssumption;

  /** 연 단위 그리드의 백분위 밴드. 팬 차트용. */
  bands: PercentileBand[];

  /** 최종 잔액 분포 요약. */
  terminal: Distribution;

  /**
   * goal 기준 성공 확률(0~1). goal 미지정 시 null.
   * 화면에서는 절대 "보장"으로 표현하지 않는다.
   */
  successProbability: number | null;

  /** 잔액이 0 이하가 된 시점 분포(개월). SoRR 계산기용. 소진 없으면 빈 배열. */
  depletionMonths: number[];

  /** 팬 차트 위에 겹쳐 그릴 대표 경로 샘플(기본 200개). */
  samplePaths: Float64Array[];

  /** 실행 메타. */
  meta: {
    pathsRun: number;
    elapsedMs: number;
    engineVersion: string;
  };
}

export interface PercentileBand {
  month: number;   // 0, 12, 24, …
  p5: number; p25: number; p50: number; p75: number; p95: number;
}

export interface Distribution {
  min: number; p5: number; p25: number; p50: number; p75: number; p95: number; max: number;
  mean: number;
}

## 3. 파라메트릭 모델의 수식 (구현 시 그대로 쓸 것)

사용자는 **연 산술평균 수익률 `μ_a`**와 **연 변동성 `σ_a`**를 입력한다.

### 3-1. 드리프트 — CAGR 기준, 충격 분포와 무관하게 공통

**`expectedReturn` 입력은 CAGR(기하평균, 연복리 수익률)로 정의한다.** 산술평균이 아니다.

```
μ_m = ln(1 + CAGR) / 12
σ_m = σ_log / sqrt(12)
```

충격의 중앙값이 0이므로(정규·t 모두 대칭) **중앙값 경로가 정확히 입력 CAGR로 복리된다.**
드리프트를 로그 공간에서 먼저 고정하므로, 충격 분포를 바꿔도 중심 경향은 유지되고 꼬리만 달라진다.

> **과거 설계와 섞이지 않도록 못 박는다.** 이전 초안에 있던
> `μ_log = ln(1+μ_a) − σ_log²/2` (산술평균 → 로그정규 변환)는 **쓰지 않는다.**
> 그 식은 산술평균 입력을 전제로 `E[gross] = 1+μ_a` 를 맞추는 보정인데,
> t 충격에서는 `exp(σz)` 의 기댓값 자체가 발산해 의미를 잃는다(3-4절).
> 입력을 CAGR로 정의하면 이 보정이 애초에 필요 없다.

**σ_log 의 정의 — (B) 단순 기준으로 확정 (2026-08-22)**

입력 `volatility` 는 **단순수익률 표준편차**로 정의하고, 엔진 내부에서 로그 공간으로 변환한다.

```
σ_log = sqrt( ln( 1 + σ² / (1 + CAGR)² ) )
σ_m   = σ_log / sqrt(12)
```

사용자가 떠올리는 "주식 변동성 15%"가 단순수익률 기준이므로 입력 의미를 사용자 직관에 맞췄다.
**변환을 빼먹으면 조용히 틀린다** — 차이가 결과를 뒤집을 만큼 크지 않으면서 꼬리에는 영향을 준다.

```
CAGR 7%,  단순 σ 15%  →  로그 σ 0.1395  (−7.0%)
CAGR 8%,  단순 σ 20%  →  로그 σ 0.1836  (−8.2%)
```

**구현 규칙**: 이 변환은 `returns.ts` 한 곳에서만 수행한다. 엔진 루프와 테스트는
`σ_m`(월 로그 표준편차)만 받는다. 입력 라벨에는 "연 변동성(단순수익률 기준)"을 명시한다.

### 3-2. 충격 `z` — 단위분산으로 정규화

```
normal:     z = N(0,1)

student-t:  z = T_ν · sqrt( (ν − 2) / ν ),   ν > 2      ← 분산 보정
            |z| > 8 이면 재추출 (수치 안전장치)
```

표준 t는 분산이 `ν/(ν−2)`이므로 **`sqrt((ν−2)/ν)`를 곱해야 사용자가 입력한 변동성이 실제로 지켜진다.**
이 보정을 빠뜨리면 df 6에서 변동성이 약 1.22배 부풀려진다. 구현 시 가장 흔한 실수 지점이다.

### 3-3. 월 수익 배수

```
월 수익 배수 = exp( μ_m + σ_m · z )
```

`σ = 0`이면 충격 분포와 무관하게 `exp(ln(1+CAGR)/12)`로 고정된다.
**즉 `volatility = 0` 회귀 앵커는 Student's t로 바꿔도 그대로 성립한다.**

### 3-4. 두꺼운 꼬리에서 주의할 점

로그수익률에 t 충격을 쓰면 `exp(σ·z)`의 **기댓값이 이론적으로 발산한다.** t의 꼬리가 지수함수를 이기기 때문이다.
실무적 귀결은 다음과 같다.

- **평균으로 보고하지 않는다.** 표본 평균은 극단 경로 몇 개에 좌우되어 실행마다 흔들린다.
  중앙값과 백분위로 보고한다 — 원래 표시 원칙과도 일치한다.
- `Distribution.mean`은 참고용으로만 두고, 화면에서 강조하지 않는다.
- `|z| > 8` 절단은 이 불안정성과 수치 안전을 위한 장치다. **절단을 적용했다는 사실을
  `ReturnAssumption`에 기록**해 결과에 동봉한다.

**절단 후 변동성 정합성** — `sqrt((ν−2)/ν)` 보정은 *절단하지 않은* t의 분산을 정확히 1로 만든다.
`|z| > 8`을 잘라내면 분산이 미세하게 다시 작아진다. df 6 기준 수치는 다음과 같다.

| 항목 | 값 |
|---|---|
| 절단 확률 `P(|z| > 8)` | `6.51e-05` (1억 표본당 약 6,506회) |
| 재추출(조건부 분포) 시 표준편차 | `0.99685` → **−0.32%** |
| 클리핑 시 표준편차 | `0.99890` → **−0.11%** |
| (참고) 분산 보정을 아예 빠뜨리면 | `1.2247` → **+22.5%** |

**계약: 재정규화하지 않는다.** 절단 오차는 −0.32%로 검증 기준 2%의 6분의 1 수준이고,
재정규화는 "보정을 한 번 더 하는" 코드를 늘려 오히려 실수 여지를 만든다.
대신 **"수치 절단으로 표본 σ가 입력값보다 최대 0.4% 작을 수 있다"**를 계약으로 명시하고,
6번 검증 테스트의 허용 오차 2%를 그대로 유지한다. 보정 누락(+22.5%)과는 자릿수가 달라
테스트가 둘을 확실히 구분한다.

> **입력 라벨에 "CAGR(연복리) 기준"임을 반드시 표기한다.** 산술평균으로 오해하면
> 장기 결과가 과대평가된다 — 산술 7% · 변동성 15%의 기하수익률은 약 5.9%로, 40년이면
> 종말자산이 배 이상 갈린다.

## 4. 월별 진행 규칙

```
for m in 0 .. months-1:
    if timing == "start": balance += cashFlow(m)
    balance *= returnFactor(m)
    if timing == "end":   balance += cashFlow(m)
    if balance <= 0:
        balance = 0
        record depletionMonth = m ; break
```

- `cashFlow(m)`은 `inflationIndexed`면 `monthlyAmount × (1 + inflationRate)^(floor(m/12))`.
- `reportBasis === "real"`이면 기록 시점에 `balance / (1 + inflationRate)^(m/12)`로 환산한다. **환산은 기록 단계에서만** 하고 진행 계산은 명목으로 돌린다(이중 할인 방지).

## 4-B. 목표 역산 — 선형 정확해 (이분 탐색 아님)

한 경로의 월 수익 배수 `r_1 … r_N`을 고정하면, **종말자산은 현금흐름 수준에 대해 아핀(affine)이다.**

```
W_T = P0 · G(0)  +  c · Σ_m ( s_m · G(m) )
      └─── A ───┘     └────── B ──────┘

G(m) = Π_{i > m} r_i     // m 시점 납입금이 만기까지 불어나는 배수
s_m                      // 현금흐름 형상 (인플레 연동 스케줄 등)
c                        // 납입 수준 스칼라 — 우리가 구하려는 값
```

경로마다 `A_j`, `B_j`를 **시뮬레이션 한 번의 패스에서 함께 누적**해두면, 그 뒤로는 재시뮬레이션이 필요 없다.

```
경로 j 는 c ≥ c_j 일 때 성공한다 (B_j > 0). 따라서 성공확률은 {c_j} 의 경험적 CDF 다.

    P(c) = #{ j : c_j ≤ c } / N

목표 확률 p 를 만족하는 최소 납입액 (정확해)
    c_j = (W* − A_j) / B_j            // 경로별 필요 납입액
    c*  = quantile( {c_j}, p )        // 정렬 후 p 분위수
```

> **분위수 방향 주의.** `p` 분위수이지 `1 − p` 가 아니다. 목표 90%면 `c_j` 의 **90번째**
> 백분위수를 쓴다. 90%를 달성하려면 "필요 납입액이 큰 경로들"까지 덮어야 하므로 상위 분위수다.
> `1 − p` 를 쓰면 90% 목표에서 10번째 백분위수를 골라 **약 10% 경로만 커버**하게 된다.
> 부호가 반대라도 결과가 그럴듯한 숫자로 나오기 때문에 눈으로는 잡히지 않는다 —
> 아래 7번 회귀 테스트가 이걸 잡는 장치다.

이분 탐색은 매 반복마다 전체 경로를 다시 훑어야 하고, 확률이 계단 함수라 경계에서 진동한다.
선형 해는 **한 번의 정렬로 끝나고, 목표 확률을 연속적으로 바꿔도 즉시 다시 답한다.**
슬라이더로 목표 확률을 움직이는 UI가 가능해진다.

**선형성이 성립하는 조건** — 경로가 상태에 따라 분기하지 않아야 한다.

| 조건 | 선형 |
|---|---|
| 적립 국면, 잔액이 0에 닿지 않음 | 성립 |
| 인출로 잔액이 0에서 클램프됨 | **깨짐** |
| 리밸런싱, 실현 과세 등 경로 의존 규칙 | **깨짐** |

따라서 **DCA·목표달성확률(3단계)은 선형 정확 역산**, 클램프나 경로 의존 규칙이 들어가는
**FIRE·SoRR·리밸런싱(4단계 이후)에서만 이분 탐색으로 폴백**한다.
엔진은 어느 쪽을 썼는지 결과에 남긴다.

```ts
export interface InversionResult {
  /** 목표 확률을 만족하는 최소 월 납입액. */
  requiredMonthlyAmount: number;
  method: "linear-exact" | "bisection";
  /** 검증용 — 그 납입액에서 실제로 나온 성공확률. */
  successProbabilityAt: number;
}
```

`SimulationResult`에 선형 계수를 선택적으로 실어 보낸다. 경로당 double 2개이므로
10,000경로에 160KB로, 재시뮬레이션 비용에 비하면 무시할 수준이다.

```ts
  /** 선형 역산용 경로별 계수. 클램프가 발생하지 않은 실행에서만 채워진다. */
  affine?: { A: Float64Array; B: Float64Array };
```

## 5. Worker 프로토콜과 성능 예산

```ts
// main → worker
{ type: "run",    id: string, input: SimulationInput }
{ type: "cancel", id: string }

// worker → main
{ type: "progress", id: string, completed: number, total: number }
{ type: "result",   id: string, result: SimulationResult }   // Float64Array 는 transfer
{ type: "error",    id: string, message: string }
```

- 진행률은 **250ms 이하 간격으로 보내지 않는다**(메시지 폭주 방지).
- 취소는 경로 루프에서 플래그를 확인해 즉시 중단.

**메모리 설계가 핵심이다.** 10,000경로 × 480개월 전체를 보관하면 4.8M × 8B ≈ 38MB로 과하다. 대신:

| 보관 대상 | 크기 | 방법 |
|---|---|---|
| 연 단위 그리드(41포인트) 전 경로 값 | 41 × 10,000 × 8B ≈ 3.3MB | 백분위 계산 후 폐기 |
| 최종 잔액 | 10,000 × 8B = 80KB | 분포 요약 |
| 소진 시점 | 소진 경로 수만큼 | 히스토그램 |
| 대표 경로 | 200 × 481 × 8B ≈ 0.8MB | 팬 차트 오버레이 |

**성능 목표**: 10,000경로 × 480개월(4.8M 스텝)을 **최신 데스크톱 브라우저에서 1초 이내**, 모바일에서 3초 이내. 스텝당 할당이 없어야 하고, 경로 버퍼는 재사용한다.

**난수**: `Math.random()`은 시드를 못 주므로 쓰지 않는다. **xoshiro128\*\* 또는 PCG32** + Box–Muller(또는 ziggurat)로 정규난수를 만든다. 시드는 입력에 포함되어 결과와 함께 저장된다.

## 6. 정확성 검증 계획

엔진은 결과를 검증할 외부 정답이 없는 계산이므로, **검증 설계를 코드보다 먼저 확정한다.**

1. **결정론 축소 테스트** — `volatility = 0`이면 기존 복리 계산기와 원 단위까지 일치해야 한다. 이게 1순위 회귀 테스트다.
2. **해석적 대조** — 로그정규 가정에서 최종 잔액의 이론적 중앙값 `P0 · exp(μ_log · T)`와 시뮬레이션 중앙값이 10,000경로 기준 오차 1% 이내.
3. **수렴 테스트** — 1,000 / 10,000 / 50,000경로에서 p50이 단조 수렴하는지. 수렴하지 않으면 난수 품질을 의심한다.
4. **시드 스냅샷** — 고정 시드로 계산한 백분위를 스냅샷으로 저장. 리팩터링 시 결과가 바뀌면 즉시 감지된다.
5. **경계 케이스** — 기간 0개월, 초기 자산 0 + 납입만, 인출만(즉시 소진), 현금흐름이 첫 달에 잔액을 넘는 경우.
6. **분산 보정 검증** — df 6 Student's t 충격으로 10,000경로를 돌렸을 때 월 로그수익률의
   표본 표준편차가 `σ_m`과 오차 2% 이내. 보정을 빠뜨리면 약 22% 초과로 즉시 잡힌다.
7. **선형 역산 대조** — 선형 해로 구한 `c*`를 실제로 넣고 재시뮬레이션했을 때
   성공확률이 목표 `p`와 일치하는지(경로 수 유한성에 따른 이산 오차 이내). 4-B절 전제가
   깨지지 않았는지 확인하는 회귀 테스트이기도 하다.
   **`p = 0.9`와 `p = 0.1`을 모두 테스트한다** — 분위수 방향이 뒤집혀 있으면 이 두 케이스가
   서로 자리를 바꾸며 즉시 드러난다. 대칭이 아닌 값을 골라야 잡힌다.

기존 계산기 감사에서 나온 교훈을 그대로 적용한다: **빈칸·음수·비현실적 값은 조용히 0으로 치환하지 말고 거부하거나 명시적으로 알린다.**

## 7. 프리셋 계약

```ts
export interface AssetPreset {
  id: string;
  label: string;            // "주식 100%", "주식 60 / 채권 40"
  expectedReturn: number;   // 연 산술평균
  volatility: number;       // 연 표준편차
  source: string;           // 출처 (기관·문서명)
  asOf: string;             // 기준일 YYYY-MM-DD
  note?: string;            // 한계·주의
}
```

**프리셋 숫자는 화면에 출처와 기준일을 함께 노출한다.** 감사에서 지적된 YMYL 결함(기준일·출처 0건)을 새 기능에서 반복하지 않기 위한 조건이다. 값을 갱신할 때는 **그때마다 1차 출처로 재확인**하고 `asOf`를 갱신한다 — 코드에 박힌 숫자를 영구 상수로 취급하지 않는다.

## 8. 이후 단계가 이 엔진을 쓰는 방식

| 단계 | 엔진 사용 방식 | 추가로 필요한 것 |
|---|---|---|
| **DCA** | `cashFlow.monthlyAmount > 0`, `goal` 없음 | 적립 금액·기간 UI, 팬 차트 |
| **목표 달성 확률** | `goal.kind = "terminal-target"` → `successProbability` + `affine` 계수 | **선형 정확 역산**(4-B절). 재시뮬 없음 |
| **FIRE** | 적립 구간 + 인출 구간을 `fromMonth`/`toMonth`로 이어 붙임 | 목표 자산 역산, 4% 룰 비교 |
| **SoRR** | `monthlyAmount < 0`, `goal.kind = "never-depleted"` | `depletionMonths` 히스토그램, 수익률 순서 위험 설명 |
| **무매도 리밸런싱** | 다자산으로 확장 필요 | `ReturnSpec` 다자산화 + 상관행렬 |
| **포트폴리오 분석** | 다자산 + 상관 | 자산별 가중치 입력 |
| **`/lab` 백테스트** | `ReturnSpec.kind = "bootstrap"` 실데이터 | 시계열 데이터셋과 갱신 파이프라인 |

> **순서 주의**: 목표달성확률을 FIRE·SoRR보다 앞에 둔다. 엔진 + DCA만으로 검증 가능한
> 최소 단위이기 때문이다. FIRE·SoRR은 적립→인출 구간 연결, 소진 추적, 성공확률 정의가
> 한꺼번에 들어가므로 뒤로 미룬다. `depletionMonths`와 `never-depleted`는 타입 계약에는
> 이미 있으므로, 나중에 구현해도 인터페이스 변경은 없다.

**다자산(6~8단계)은 1단계 인터페이스에 미리 넣지 않는다.** 단, `ReturnSpec`을 유니온 타입으로 두었으므로 `{ kind: "multi-asset", weights, correlations }`를 나중에 추가해도 기존 코드가 깨지지 않는다.

## 9. 표시 원칙 (YMYL)

- 성공 확률은 **가정에 대한 조건부 확률**이다. "○○% 확률로 달성"이 아니라 "이 가정에서 ○○% 시나리오가 목표를 달성"으로 쓴다.
- 팬 차트의 상단 밴드를 기대값처럼 보이게 두지 않는다. 중앙값을 기본 강조한다.
- 세금·수수료 미반영이면 결과 카드에 명시한다(기존 계산기의 미해결 지적사항 A 트랙과 동일 원칙).
- 입력 가정과 기준일을 결과와 함께 항상 노출한다.

## 10. 착수 전 남은 결정

1. **프리셋 수치의 출처를 무엇으로 할지** — 국내 접근 가능한 장기 수익률 통계가 마땅치 않다. 해외 지수 기반으로 갈지, 범위로 제시할지 결정 필요.
2. **인플레이션 기본값** — 고정값을 둘지, 사용자 입력만 받을지. 고정값이면 출처·기준일 필요.
3. **세금 처리 위치** — 엔진 내부에서 매년 과세할지, 표시 단계에서 일괄 적용할지. 장기 시뮬레이션에서 차이가 크다.
4. **결과 공유 방식** — 시드와 입력을 URL 쿼리로 직렬화할지. 하면 재현성이 생기지만 URL에 개인 재무 정보가 들어간다(감사 지침상 URL에 민감 정보 금지 → **로컬 저장 우선 검토**).
5. **`/lab` 데이터셋 확보 경로** — 8단계에서만 필요하지만 라이선스 확인이 선행돼야 한다.
6. **`df` 기본값 6 유지 여부** — 권장 범위 5~7 안에서 프리셋별로 다르게 둘지, 전역 고정할지.
   자산군마다 꼬리 두께가 다르므로 프리셋에 함께 넣는 쪽이 정확하지만 설명 부담이 는다.
